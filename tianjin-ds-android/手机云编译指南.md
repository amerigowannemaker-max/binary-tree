# 只用手机触发云端 APK 编译

本工程把210道填空题封装为 Tauri 2 + SQLite App，GitHub Actions 会在云端 Linux 执行 Android SDK / NDK + Rust 的 APK 编译。**这不是已编译的 APK**；流程未在此环境中实测。第一次构建如果报错，可在仓库 Actions 日志中查看缺失的依赖和构建报错。

## 路线A：用 ChatGPT Work 辅助

1. 把本 ZIP 文件交给 Work，并让 Work 在你授权的 GitHub 仓库中上传（解压后的）完整工程。
2. 把 `.github/workflows/android-apk.yml` 提交到 GitHub 仓库的默认分支。
3. 在手机 GitHub 网页或 App 中进入仓库 -> Actions -> 「安卓 APK（手机可触发）」-> Run workflow。
4. 构建成功后进入该次执行页面，下方 Artifacts 下载 `tianjin-ds-2027-android-debug-apk` 压缩包，解压获取 APK，手机按提示安装。

## 路线B：手机 Termux 上传工程

如果已经会使用 Git 的话，可用 Termux 的 `git` 把解压后的项目 push 到 GitHub。GitHub Actions 在服务器上构建，因此手机不用安装 Rust、Android SDK 和 NDK。

## 为什么先出 debug APK？

它可以自动由 Gradle 使用临时 debug key 签名，适合先验证 APP 是否能打开、SQLite 是否能写入以及退出重进能否续答。Android 官方文档说明 debug APK 通常已经带有调试签名，可以直接安装。

**重要：不能把云端每次自动生成的 debug APK 当长期更新方案。** 每次 GitHub Actions 使用的新 runner 可能生成不同的 debug 签名密钥。签名不同的同包名 APK 不能直接覆盖更新，卸载旧版又会删掉 SQLite 记录。正式长期使用前，必须生成并安全保管一份固定的 Android 签名密钥，配置到仓库 Secrets 并接入稳定签名工作流。不要上传 `.jks`、密码到仓库；不要把签名密钥发送到聊天。

## 关于云端与手机

Work 云端容器是否能直接编译取决于其 Android SDK/NDK/Rust 安装能力和网络权限；不保证每个环境能直接出 APK。GitHub Actions 则是更标准的 CI 方案。Windows EXE 需要在 Windows runner 上额外配置另一条工作流；SQLite 的数据默认不会自动在手机和电脑之间同步。

## 首次验证清单

- 在手机打开 APP、输入答案、点“下一题”。
- 答对跳到下一题，答错留在本题并显示解析。
- 退出 APP，再次打开，确认继续刚才题号。
- 断网后再打开，确认题库仍正常。
- 错题集、收藏和统计数据是否持续。
